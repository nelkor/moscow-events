# Техническая документация

Учебный бэкенд на FastAPI с PostgreSQL и PostGIS для локальной работы
с московскими событиями и синтетическими бронированиями.

- [Спецификация OpenAPI с описаниями методов, параметров и примерами](openapi.yml)
- [О проекте](../README.md)

Фронтенд и API доступны через один NGINX. Браузер обращается к API
относительными URL `/api/v1/...`. NGINX фронтенда, бэкенд и БД подключены
к общей Docker-сети.

## Запуск в Docker

Все команды ниже выполняются из корня репозитория.

Соберите образ:

```sh
docker build -t moscow-events-backend:1.0.0 .
```

Скопируйте [`.env.example`](../.env.example) в `.env` и задайте параметры подключения к БД:

```dotenv
PG_HOST=db
PG_PORT=5432
PG_DB_NAME=moscow_events
PG_USER_NAME=postgres
PG_USER_PASSWORD=change-me
```

`PG_HOST` по умолчанию равен `db` — имени контейнера или сервиса PostgreSQL
в общей Docker-сети. `PG_PORT` по умолчанию равен `5432`.
`localhost` внутри контейнера указывает на сам бэкенд. Пароль передаётся
как есть, включая специальные символы.

База данных должна быть создана заранее. На сервере PostgreSQL должно быть
установлено расширение PostGIS; для учебной среды подходит образ
`postgis/postgis:17-3.6`. Пользователю БД нужны права на создание таблиц
и расширения PostGIS (либо расширение должен заранее создать администратор).

Запустите контейнер в существующей общей сети (в примере — `app-network`):

```sh
docker run --rm --name backend --network app-network --env-file .env moscow-events-backend:1.0.0
```

Подставьте имя своей сети вместо `app-network`. NGINX и PostgreSQL должны
быть подключены к этой же сети. Каждую переменную также можно передать
отдельным параметром Docker, например `-e PG_DB_NAME=moscow_events`.

## Проксирование через NGINX

Добавьте в блок `server` NGINX фронтенда:

```nginx
location /api/ {
    proxy_pass http://backend:8000;
    proxy_set_header Host $http_host;
}

location ~ ^/(docs|redoc|openapi\.json|health)(/|$) {
    proxy_pass http://backend:8000;
    proxy_set_header Host $http_host;
}
```

`backend` — имя контейнера или сервиса бэкенда. В `proxy_pass` после порта
нет `/`: исходный путь `/api/v1/...` передаётся приложению целиком.
Фронтенд использует, например, `fetch('/api/v1/events')`. Заголовки
`Content-Type` и `Idempotency-Key` NGINX передаёт бэкенду автоматически.

Через адрес NGINX доступны:

- Swagger UI: `/docs` (схема — `/openapi.json`)
- ReDoc: `/redoc`
- Проверка работы процесса: `/health/live`
- Проверка подключения к БД и готовности API: `/health/ready`

Приложение автоматически применяет миграцию и заполняет пустую БД небольшим
демонстрационным набором. Существующие данные сохраняются. Если БД ещё
недоступна, подключение повторяется автоматически, а `/health/ready` возвращает
HTTP 503 до успешной инициализации. Docker healthcheck проверяет этот адрес.

## Переменные окружения

| Переменная | Назначение | По умолчанию |
| --- | --- | --- |
| `PG_HOST` | Адрес PostgreSQL в Docker-сети | `db` |
| `PG_PORT` | Порт PostgreSQL, целое число от 1 до 65535 | `5432` |
| `PG_DB_NAME` | Имя базы данных | Обязательная |
| `PG_USER_NAME` | Имя пользователя PostgreSQL | Обязательная |
| `PG_USER_PASSWORD` | Пароль пользователя PostgreSQL | Обязательная |
| `SEED_MODE` | `sample` — демоданные, `empty` — пустой каталог | `sample` |

Если обязательная переменная отсутствует или пуста, приложение завершает
запуск с сообщением о недостающих настройках. Некорректный порт также
останавливает запуск. `SEED_MODE` — дополнительная необязательная настройка
начальных данных.

В образ включаются приложение, SQL-миграция и зависимости. Данные для
подключения передаются при запуске; `.env`, локальное виртуальное окружение,
кэши и тесты исключены из контекста сборки. Приложение работает от отдельного
пользователя без прав root.

## Работа клиента с API

Клиент получает данные через `/api/v1`, обходит коллекции по страницам
и использует UUID и справочники из ответов сервера. Он должен работать
с любым совместимым набором, включая пустой, без привязки к названиям
и количеству записей демонстрационной БД. Учебную точку отсчёта времени
`reference_time` возвращает `GET /api/v1/meta`; после переноса БД она сохраняется.

Рейтинги, прогнозы, подбор нескольких событий, поиск дубликатов и конфликтов
расписания реализует клиент, используя исходные данные и универсальные
агрегаты API. CSV также разбирает клиент и отправляет последовательными
пакетами `POST /api/v1/events/bulk` до 200 операций; атомарность действует
внутри одного пакета. Адрес и координаты задаются отдельно, их соответствие
проверяет автор данных; геокодирования и маршрутизации в сервере нет.

## Хранение и перенос БД

Для учебного окружения используйте backend `1.0.0`, схему `2026_01`,
PostgreSQL 17 и PostGIS 3.6. Фактические версии и размеры набора возвращает
`GET /api/v1/dataset/summary`. При работе на другой CPU-архитектуре проверьте
запуск выбранного образа PostGIS в своём окружении.

В своём `compose.yml` или команде запуска PostgreSQL подключите именованный
volume к `/var/lib/postgresql/data` и оставьте БД во внутренней Docker-сети.
Данные сохраняются при пересоздании контейнеров, пока сохраняется volume;
получение исходного seed заново требует явной очистки учебной БД с потерей
её данных. Для обмена используйте логический дамп схемы и данных, включая
метаданные набора, а не файлы volume.

Пример экспорта для контейнера `db`, пользователя `postgres` и БД
`moscow_events` (подставьте свои значения):

```sh
docker exec db pg_dump -U postgres -d moscow_events -Fc --no-owner --no-acl -f /tmp/dataset.dump
docker cp db:/tmp/dataset.dump ./dataset.dump
```

Вместе с `dataset.dump` передавайте `dataset-manifest.json`: сохраните в него
ответ `GET /api/v1/dataset/summary` и добавьте поле `sha256` с контрольной
суммой дампа. На время экспорта и получения счётчиков приостановите изменения
данных, чтобы манифест соответствовал архиву. Получатель проверяет источник,
контрольную сумму и совместимость версий backend, схемы и PostgreSQL/PostGIS.

Восстанавливайте дамп в новую изолированную учебную БД, пока backend для неё
не запущен и не создал seed:

```sh
docker exec db createdb -U postgres -T template0 moscow_events_imported
docker cp ./dataset.dump db:/tmp/dataset.dump
docker exec db pg_restore -U postgres -d moscow_events_imported --no-owner --no-acl --single-transaction --exit-on-error /tmp/dataset.dump
```

Укажите `PG_DB_NAME=moscow_events_imported` в `.env` и запустите backend
с этими настройками. Проверьте успешный ответ `/health/ready`, совпадение
`dataset.dataset_id`, `schema_version`, `reference_time` и `counts` в
`/api/v1/dataset/summary` с манифестом, а также работу `/api/v1/events/nearby`.
Повторный запуск сохраняет импортированные данные и не добавляет seed.

## Нагрузочные проверки

Ориентир для испытаний — 10 000 мероприятий, 2 000 площадок и 100 000
синтетических бронирований; такой набор создаётся отдельно для тестирования.
Целевые времена после прогрева: список до 500 мс, геопоиск до 1 с,
агрегаты до 2 с. Это ориентиры испытаний, зависящие от окружения.
