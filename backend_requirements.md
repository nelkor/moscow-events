# Технические требования к универсальному backend «Московская афиша»

**Тип документа:** техническое задание / контракт учебного API  
**Версия документа:** 1.0 (проект)  
**Назначение:** единый backend для практических работ по Git, Docker, REST API и разработке frontend  
**Целевая аудитория:** преподаватель — разработчик backend; студенты — разработчики клиентских приложений  
**Предметная область:** мероприятия, артисты, площадки, расписание, цены и бронирования в Москве.

> **Главное ограничение:** backend создаёт лишь небольшой демонстрационный набор данных. **Большой каталог автоматически не генерируется и вместе с backend не распространяется.** Расширенные наборы возникают в результате работы студентов (ввод, редактирование, массовые операции, импорт) и передаются другим студентам отдельными дампами PostgreSQL.

---

## 1. Цель и границы системы

### 1.1. Назначение

Backend должен обеспечивать единый стабильный API для разных веб-приложений:

- **управление**: календарь организатора, редактор мероприятий, управление площадками и артистами, бронирования, цены, серия мероприятий, массовое редактирование, импорт, аудит качества;
- **подбор**: события рядом с заданной точкой, по бюджету, жанру, времени, возрастному ограничению, вместимости; поиск событий для компании, планирование нескольких мероприятий за вечер;
- **аналитика**: цены, востребованность жанров, заполняемость, выручка, бронирования, сравнение площадок и артистов, география событий, временные распределения, выявление аномалий и простые прогнозы.

Все студенческие клиенты должны работать с **одной схемой БД, одной версией API и одним образом backend**, независимо от варианта задания и источника данных.

### 1.2. Разделение ответственности

**Backend обязан:**

1. Хранить и предоставлять предметные данные.
2. Реализовать CRUD и массовые изменения.
3. Проверять целостность и обязательные бизнес-инварианты.
4. Выполнять поиск, фильтрацию, сортировку и пагинацию.
5. Выполнять **геопоиск по радиусу** через PostGIS.
6. Предоставлять универсальные агрегаты для больших наборов данных.
7. Инициализировать пустую БД схемой и небольшим набором данных.
8. Сохранять пользовательские изменения и поддерживать перенос дампов БД.
9. Предоставлять машиночитаемую документацию API и сведения о версии схемы.

**Frontend студента обязан:**

- реализовать интерфейс своего сценария, проверку ввода и обработку ошибок;
- интерпретировать и визуализировать результаты API;
- самостоятельно выполнять специфические для варианта алгоритмы (подбор, ранжирование, сравнение, аномалии, прогноз и т. п.), используя данные и общие агрегаты API;
- **не обращаться к БД напрямую** и не зависеть от заранее известных ID, названий и количества записей.

### 1.3. Что НЕ входит в обязательную функциональность

- Настоящая покупка билетов, платёжные системы и персональные данные покупателей.
- Регистрация, авторизация, разграничение ролей и многопользовательское администрирование.
- Геокодирование текстового адреса по стороннему API.
- Маршрутизация по улицам, время в пути на метро или пешком.
- Рекомендации с машинным обучением и интеграции с внешними афишами.
- Отдельный backend для каждого варианта.
- Генерация большого набора данных командой, переменной окружения или скрытым API.

Указанные функции можно добавить позже, но они **не должны требоваться для базовой практической работы**.

## 2. Общая архитектура и поставка

### 2.1. Контейнеры

Обязательная учебная конфигурация включает:

1. `db`: PostgreSQL с расширением PostGIS, с именованным Docker volume;
2. `backend`: опубликованный преподавателем Docker-образ приложения;
3. `frontend`: образ, собираемый из исходного кода студента.

Студенты создают собственный `compose.yml`. Backend получает параметры подключения через переменные окружения: `PG_HOST` (по умолчанию `db`), `PG_PORT` (по умолчанию `5432`), обязательные `PG_DB_NAME`, `PG_USER_NAME` и `PG_USER_PASSWORD`. Пароль передаётся как есть; пустые обязательные значения и некорректный порт останавливают запуск с ошибкой конфигурации.

NGINX фронтенда и backend работают в одной Docker-сети. Браузер получает фронтенд и API через один адрес NGINX; запросы `/api/v1/...` проксируются в backend с сохранением исходного пути.

### 2.2. Рекомендуемый стек

- PostgreSQL **17** и PostGIS **3.6** — один зафиксированный набор версий на весь поток.
- Для стандартной x86-64 среды: `postgis/postgis:17-3.6`.
- Backend: любой зрелый стек с поддержкой OpenAPI и миграций (например, FastAPI + SQLAlchemy + Alembic). Выбор языка не влияет на HTTP-контракт.
- REST/JSON поверх HTTP; спецификация **OpenAPI 3.1**.

**Почему PostGIS оправдан:** готовый контейнер существенно упрощает установку; тип `geography(Point, 4326)` позволяет искать в радиусе, указывая расстояние в метрах. Это полезнее и точнее для задания, чем вручную вычислять расстояние между координатами.

**Совместимость архитектур:** основной образ `postgis/postgis` на момент подготовки документа заявляет поддержку `amd64`. Если среди студентов есть устройства `arm64` (например, Apple Silicon), преподаватель **до выдачи задания** обязан проверить выбранный образ на такой машине, использовать проверенный multi-arch вариант/собственную сборку либо задокументировать поддерживаемую эмуляцию. Не следует полагаться на экспериментальный сторонний образ без предварительного тестирования.

### 2.3. Версионирование

- Базовый путь API: `/api/v1`.
- Образ backend публикуется с **фиксированным тегом**, например `1.0.0` (не `latest`).
- Схема БД имеет версию миграций (например, `2026_01`).
- Преподаватель фиксирует совместимость: `backend version` ↔ `schema version` ↔ `PostgreSQL/PostGIS versions`.
- Обновления в пределах одной лабораторной не должны ломать существующие дампы или запросы студентов.

## 3. Доменная модель

### 3.1. Общие правила

- Первичные ключи всех предметных сущностей: **UUID**, генерируемые сервером.
- Даты событий и бронирований: `timestamptz`, в API — ISO 8601 с часовым смещением/`Z`.
- Пользовательский часовой пояс: `Europe/Moscow` (MSK); frontend отвечает за локальное отображение.
- Цены: **целые рубли**, без копеек (`price_rub: integer`), значение `0` допустимо.
- Возрастные категории: `0`, `6`, `12`, `16`, `18` (смысл «0+», «6+» и т. д.).
- Перечисления (статусы, жанры, районы) имеют **стабильные машинные коды** и человекочитаемые русские названия.
- Каждая изменяемая сущность содержит `created_at` и `updated_at`.
- Все внешние ключи и существенные поля индексируются.

### 3.2. `Artist` — артист / исполнитель

| Поле | Тип | Обяз. | Смысл |
|---|---|---:|---|
| `id` | UUID | да | Идентификатор |
| `name` | string (1–200) | да | Имя или название коллектива |
| `description` | text | нет | Описание |
| `primary_genre_code` | string | нет | Основной жанр исполнителя |
| `image_url` | URL | нет | Ссылка на иллюстрацию, без загрузки в backend |
| `created_at`, `updated_at` | datetime | да | Аудит |

- Похожие/совпадающие названия **не запрещены**: это позволяет выполнять задания по поиску дубликатов.
- Один артист может участвовать во множестве мероприятий.
- В минимальной модели у каждого мероприятия **один основной артист**. Несколько исполнителей на одном мероприятии — необязательное расширение, не требуемое для 36 исходных вариантов.

### 3.3. `Venue` — площадка

| Поле | Тип | Обяз. | Смысл |
|---|---|---:|---|
| `id` | UUID | да | Идентификатор |
| `name` | string (1–200) | да | Название |
| `city` | string | да | Для лабораторной — `Москва` |
| `district_code` | string | да | Код административного округа/района из справочника |
| `street` | string | да | Улица/проезд/площадь |
| `house` | string | да | Номер дома/строения |
| `formatted_address` | string | да | Полный адрес для показа на карте и в карточке |
| `latitude` | number | нет* | Широта в WGS84 |
| `longitude` | number | нет* | Долгота в WGS84 |
| `capacity` | integer > 0 | да | Вместимость площадки |
| `description` | text | нет | Сведения о площадке |
| `created_at`, `updated_at` | datetime | да | Аудит |

\* Координаты задаются **только парой**: либо обе, либо обе отсутствуют. Отсутствие допускается для чернового каталога и заданий по контролю качества. Площадка без координат исключается из пространственного поиска и GeoJSON.

**Физическое хранение:** одно авторитетное поле `location geography(Point, 4326)`; `latitude` и `longitude` в API являются представлением этой точки. Не допускать рассинхронизации между двумя копиями координат.

Рекомендуемый индекс:

```sql
CREATE INDEX venues_location_gix ON venues USING GIST (location);
```

### 3.4. `EventSeries` — группа связанных событий

Нужна для задания «конструктор регулярных мероприятий».

| Поле | Тип | Обяз. | Смысл |
|---|---|---:|---|
| `id` | UUID | да | Идентификатор серии |
| `name` | string | да | Название серии |
| `description` | text | нет | Описание |
| `created_at`, `updated_at` | datetime | да | Аудит |

Периодичность (каждую пятницу и пр.) **может вычислять frontend**; backend обязан позволять создать серию и привязать к ней множество событий одной атомарной массовой операцией.

### 3.5. `Event` — мероприятие

| Поле | Тип | Обяз. | Смысл |
|---|---|---:|---|
| `id` | UUID | да | Идентификатор |
| `title` | string (1–250) | да | Название |
| `description` | text | нет | Описание |
| `artist_id` | UUID | да | Основной исполнитель |
| `venue_id` | UUID | да | Площадка |
| `series_id` | UUID/null | нет | Серия мероприятий |
| `genre_code` | string | да | Жанр данного мероприятия |
| `starts_at` | datetime | да | Начало |
| `ends_at` | datetime | да | Окончание; строго позже начала |
| `price_rub` | integer ≥ 0 | да | Текущая цена одного билета |
| `age_rating` | enum | да | `0/6/12/16/18` |
| `ticket_quota` | integer > 0 | да | Количество билетов в продаже, не выше вместимости площадки |
| `status` | enum | да | `draft`, `published`, `cancelled`, `archived` |
| `tags` | string[] | нет | Произвольные метки (например, «вечерний», «семейный») |
| `created_at`, `updated_at` | datetime | да | Аудит |

**Вычисляемые поля ответа** (не являются независимыми изменяемыми колонками):

- `sold_tickets` — сумма билетов в **подтверждённых** бронированиях;
- `available_tickets = ticket_quota - sold_tickets`;
- `occupancy_percent = sold_tickets / ticket_quota * 100`;
- `venue`, `artist` — краткие вложенные представления при `include=venue,artist`.

Правила жизненного цикла:

- `draft` может быть неполным только по **необязательным** полям, но должен выполнять базовые ограничения модели.
- `published` виден в публичных подборках; `draft` и `archived` не видны в них по умолчанию.
- `cancelled` остаётся в истории и аналитике, но не доступен для новых бронирований.
- `archived` сохраняется для аудита и поиска дубликатов.
- Удаление мероприятия с бронированиями запрещается (HTTP `409`); применяется отмена или архивация.
- Перекрытия по времени у артиста/площадки **не являются жёстким ограничением БД**, чтобы студенты могли строить системы поиска и исправления конфликтов. Их можно возвращать в необязательных предупреждениях предпросмотра.

### 3.6. `Reservation` — бронирование

| Поле | Тип | Обяз. | Смысл |
|---|---|---:|---|
| `id` | UUID | да | Идентификатор |
| `event_id` | UUID | да | Мероприятие |
| `quantity` | integer ≥ 1 | да | Количество билетов |
| `unit_price_rub` | integer ≥ 0 | да* | Цена **на момент бронирования** |
| `total_price_rub` | integer ≥ 0 | да* | `quantity * unit_price_rub` |
| `status` | enum | да | `confirmed`, `cancelled` |
| `booked_at` | datetime | да | Время создания |
| `cancelled_at` | datetime/null | нет | Время отмены |
| `created_at`, `updated_at` | datetime | да | Аудит |

\* При создании через API `unit_price_rub` и `total_price_rub` вычисляются **на сервере** и не принимаются от клиента.

Требования:

1. Создание бронирования — **атомарная операция**, не допускающая перепродажи билетов при одновременных запросах (транзакция и блокировка строки мероприятия либо эквивалентный механизм).
2. Новые бронирования допускаются только для `published` мероприятия при наличии нужного остатка.
3. При изменении текущей цены мероприятия уже созданные бронирования сохраняют исходную цену.
4. При отмене бронирования место освобождается; запись не удаляется.
5. При отмене мероприятия все связанные подтверждённые бронирования переводятся в `cancelled` в **одной транзакции**.
6. Синтетические исторические бронирования стартового набора могут относиться к прошедшим событиям; их создание не означает реальной оплаты.
7. Имя покупателя, телефон, email и платежные реквизиты **не хранятся**.

### 3.7. `DatasetMetadata` — происхождение данных

Одна служебная запись на БД:

| Поле | Назначение |
|---|---|
| `schema_version` | Версия схемы |
| `dataset_id` | UUID конкретного набора |
| `dataset_kind` | `sample`, `student_created`, `imported` |
| `sample_seed_version` | Версия стартового генератора |
| `reference_time` | Зафиксированная учебная дата/время для воспроизводимых сценариев |
| `created_at` | Первое создание набора |
| `source_dataset_id` | Идентификатор предыдущего набора, если импортирован |
| `description` | Необязательное описание |

Метаданные должны переживать экспорт/импорт. Запрещено использовать `dataset_kind` для ограничения работы API: любой frontend обязан одинаково обслуживать любой совместимый набор данных.

## 4. ГИС, адреса и географический поиск

### 4.1. Формат координат

- Система координат: **WGS84, EPSG:4326**.
- В обычном JSON API передаются отдельные ключи `latitude` и `longitude`.
- Широта: от `-90` до `90`; долгота: от `-180` до `180`.
- В **PostGIS `ST_MakePoint` сначала идёт долгота, потом широта**.
- В **GeoJSON** координаты точки имеют вид `[longitude, latitude]`.
- Адрес и координаты — независимые атрибуты: геопоиск выполняется **по координатам**, а не по тексту адреса.

Пример условного объекта площадки (координаты иллюстративные; точность конкретного адреса нужно проверять вручную):

```json
{
  "name": "Учебная концертная площадка",
  "city": "Москва",
  "district_code": "CAO",
  "street": "Тверская улица",
  "house": "1",
  "formatted_address": "Россия, Москва, Тверская улица, 1",
  "latitude": 55.7558,
  "longitude": 37.6173,
  "capacity": 200
}
```

### 4.2. Заполнение координат

- Студент вправе вручную скопировать координаты из картографического интерфейса и вставить их в поля широты и долготы.
- Backend **не обязан** определять координаты по адресу и не зависит от ключей Google Maps, Яндекс Карт, OSM или другого поставщика.
- Клиент может показывать выбранную точку на карте для визуальной проверки.
- Backend валидирует диапазоны, наличие полной пары и невозможность `NaN`/`Infinity`.
- Для упражнений на контроль качества допускаются площадки **без координат**, но в опубликованном учебном каталоге большинство площадок должны иметь корректную точку.
- За корректность фактического соответствия адреса и координат отвечает вводящий их человек; автоматическая адресная верификация не входит в базовый объём.

### 4.3. Поиск мероприятий в радиусе — обязательная готовая функция

**Endpoint:** `GET /api/v1/events/nearby`

Обязательные query-параметры:

- `latitude` — широта искомой точки;
- `longitude` — долгота искомой точки;
- `radius_m` — радиус в **метрах**, целое число от `1` до `100000`.

Дополнительные параметры: `starts_from`, `starts_to`, `genre_code`, `price_min`, `price_max`, `age_max`, `tickets_min`, `status`, `page`, `page_size`.

Поведение:

1. Отбирать мероприятия по **координатам их площадок**.
2. Включать площадки на границе заданного радиуса.
3. По умолчанию учитывать **только `published`**, если `status` не задан явно.
4. Не подмешивать неявный фильтр по будущим датам: клиент задаёт период самостоятельно, используя `reference_time` из `/meta` при необходимости.
5. Возвращать `distance_m` для каждого мероприятия и сортировать по возрастанию расстояния, затем по дате и ID.
6. Исключать площадки без координат; не вызывать внешние API.
7. Возвращать расстояние **по земной поверхности (геодезическое)**, а не путь по дорогам и не время в пути.
8. Применять пагинацию **после** пространственных и обычных фильтров.

Пример запроса:

```http
GET /api/v1/events/nearby?latitude=55.7558&longitude=37.6173&radius_m=3000&genre_code=concert&page=1&page_size=20
```

Фрагмент ответа:

```json
{
  "data": [
    {
      "id": "87cc5a69-a922-4b97-8999-bebc253bd3cd",
      "title": "Музыкальный вечер",
      "starts_at": "2027-03-21T19:00:00+03:00",
      "price_rub": 1400,
      "venue": {
        "id": "e1b5ff36-b8d9-4f87-a9df-c10715a7ca89",
        "name": "Учебная концертная площадка",
        "formatted_address": "Россия, Москва, Тверская улица, 1",
        "latitude": 55.7558,
        "longitude": 37.6173
      },
      "distance_m": 0.0
    }
  ],
  "meta": { "page": 1, "page_size": 20, "total": 1 }
}
```

### 4.4. Реализация на стороне PostGIS

Требуется тип `geography(Point, 4326)`, GiST-индекс на `venues.location` и применение `ST_DWithin` для отбора.

Иллюстрация принципа запроса (без остальных фильтров):

```sql
SELECT
  e.id,
  ST_Distance(
    v.location,
    ST_SetSRID(ST_MakePoint(:longitude, :latitude), 4326)::geography
  ) AS distance_m
FROM events e
JOIN venues v ON v.id = e.venue_id
WHERE v.location IS NOT NULL
  AND e.status = 'published'
  AND ST_DWithin(
    v.location,
    ST_SetSRID(ST_MakePoint(:longitude, :latitude), 4326)::geography,
    :radius_m
  )
ORDER BY distance_m, e.starts_at, e.id;
```

Расстояние считается PostGIS, а не формулой JavaScript. При небольшом seed индекс может быть незаметен, но должен существовать для дальнейших пользовательских баз.

### 4.5. Данные для карт

**Обязательные endpoints:**

- `GET /api/v1/venues/geojson`
- `GET /api/v1/events/geojson`

Ответ: валидный `GeoJSON FeatureCollection` с `geometry.type = "Point"`, координатами `[longitude, latitude]`, `id` сущности и `properties` (название, категория, время, цена и пр.).

Поддержать фильтр `bbox=west,south,east,north`; для событий — также фильтры из `/events` и разумный `limit` (например, максимум 1000 объектов для карты). Обычный JSON API остаётся основным источником подробных данных.

## 5. REST API: обязательные операции

### 5.1. Служебные методы и справочники

| Метод и путь | Назначение |
|---|---|
| `GET /health/live` | Процесс приложения запущен |
| `GET /health/ready` | БД доступна, схема применена, PostGIS готов |
| `GET /api/v1/meta` | Версии, `reference_time`, доступные функции, сведения о наборе |
| `GET /api/v1/meta/genres` | Справочник жанров |
| `GET /api/v1/meta/districts` | Справочник московских округов/районов |
| `GET /api/v1/meta/age-ratings` | Возрастные ограничения |
| `GET /openapi.json` | Машиночитаемая спецификация |
| `GET /docs` | Интерактивная документация API (рекомендуется) |

### 5.2. CRUD

Для `artists`, `venues`, `events`, `series`:

```http
GET    /api/v1/{resource}
GET    /api/v1/{resource}/{id}
POST   /api/v1/{resource}
PATCH  /api/v1/{resource}/{id}
DELETE /api/v1/{resource}/{id}
```

Для `reservations`:

```http
GET    /api/v1/reservations
GET    /api/v1/reservations/{id}
POST   /api/v1/reservations
PATCH  /api/v1/reservations/{id}
```

- У бронирований через `PATCH` меняется **только статус** (`confirmed → cancelled`), повторная отмена идемпотентна. Созданные бронирования и исторические цены не редактируются произвольно.
- `DELETE` артистов/площадок, на которые ссылаются события, возвращает `409 Conflict`.
- `DELETE` события с бронями возвращает `409 Conflict`; для обычного снятия с афиши используется `archived` или `cancelled`.
- Успешное создание возвращает `201` и объект, обновление — `200`, физическое удаление — `204`.

### 5.3. Списки: единые правила

Каждый endpoint списка:

- принимает `page` (с 1) и `page_size` (по умолчанию 25, максимум 100);
- возвращает `data` и `meta: {page, page_size, total}`;
- поддерживает документированную сортировку (`sort=starts_at` или `sort=-price_rub`);
- использует стабильный вторичный порядок по `id`;
- возвращает пустой массив и `total: 0`, если совпадений нет;
- не требует знания количества страниц заранее.

`GET /events` обязательно поддерживает фильтры:

| Параметр | Смысл |
|---|---|
| `q` | Поиск по названию/описанию, без учёта регистра |
| `artist_id`, `venue_id`, `series_id` | Точные ссылки |
| `genre_code` | Жанр |
| `district_code` | Округ/район площадки |
| `status` | Статус; в общем CRUD-списке по умолчанию все статусы |
| `starts_from`, `starts_to` | Начало события в полуинтервале `[from, to)` |
| `price_min`, `price_max` | Стоимость одного билета, включительно |
| `age_max` | Мероприятия, допустимые для посетителя этого возраста |
| `tickets_min` | Минимум доступных билетов |
| `sort` | `starts_at`, `price_rub`, `title`, `created_at` и обратные варианты |
| `include` | Опционально: `venue`, `artist`, `availability` |

`GET /reservations` обязательно поддерживает `event_id`, `status`, `booked_from`, `booked_to`, `sort` и пагинацию. `GET /venues` — `district_code`, `q`, `capacity_min`, `has_coordinates`; `GET /artists` — `q`, `primary_genre_code`.

Никакие студенческие варианты не должны зависеть от фильтрации «только первые 100 записей»: каждую коллекцию можно обойти по страницам.

### 5.4. Бронирование

Пример запроса:

```http
POST /api/v1/reservations
Content-Type: application/json
Idempotency-Key: 7b0198e6-7cee-4303-9a93-cc7508b4bb61

{
  "event_id": "87cc5a69-a922-4b97-8999-bebc253bd3cd",
  "quantity": 3
}
```

- **Обязательна** поддержка `Idempotency-Key` для создания бронирований: повтор запроса с тем же ключом и тем же телом не должен создавать второе бронирование; тот же ключ с другим телом — `409`.
- Если доступно только два места, ответ `409` с машинным кодом `INSUFFICIENT_TICKETS`.
- Доступность билетов и снимок цены определяет сервер.

### 5.5. Атомарные массовые изменения

**Endpoint:** `POST /api/v1/events/bulk`

Поддержать до 200 операций за запрос:

- `create` — создать событие;
- `update` — частично изменить существующее;
- `archive` — архивировать существующее.

Общий формат:

```json
{
  "dry_run": true,
  "operations": [
    {
      "op": "update",
      "id": "87cc5a69-a922-4b97-8999-bebc253bd3cd",
      "fields": { "price_rub": 1500 }
    }
  ]
}
```

Требования:

1. `dry_run=true` проверяет все операции и возвращает прогнозируемые изменения/ошибки **без записи в БД**.
2. `dry_run=false` применяет весь корректный пакет в **одной транзакции**: либо всё, либо ничего.
3. Ответ сообщает число созданных/изменённых/архивированных записей и их ID.
4. При ошибке указывается номер операции и код ошибки.
5. Клиентский импорт CSV реализуется через преобразование строк файла в эти операции; отдельный сервис импорта CSV на backend **не обязателен**.
6. Для больших CSV frontend отправляет несколько последовательных пакетов. Атомарность гарантируется **внутри одного пакета**, но не всей загрузки из нескольких пакетов.
7. Для повторяемых запросов записи использовать `Idempotency-Key` либо иной явно документированный механизм защиты от повторного применения.

Дополнительно: при создании серии сначала `POST /series`, затем пакет `create` с одинаковым `series_id`.

## 6. Универсальные аналитические функции

Backend не должен иметь специальных методов «посчитать вариант А11» или «найти лучший вечер». Вместо них он обеспечивает чтение исходных данных и **набор универсальных агрегатов**, достаточных для масштабных баз.

### 6.1. `GET /api/v1/analytics/events`

Параметры:

- фильтры дат начала, жанра, артиста, площадки, района, статуса, цены;
- `group_by=none|genre|district|venue|artist|age_rating|month|weekday|hour`;
- `metrics=event_count,avg_price_rub,median_price_rub,min_price_rub,max_price_rub,ticket_quota,sold_tickets,occupancy_percent` (список через запятую).

Требования:

- `event_count` — число подходящих мероприятий;
- `avg_price_rub` — обычное арифметическое среднее текущих цен мероприятий (не взвешенное по числу билетов);
- `median_price_rub` — медиана текущих цен;
- `occupancy_percent` для группы — `SUM(sold_tickets) / SUM(ticket_quota) * 100`, **не среднее процентов отдельных мероприятий**;
- у агрегатов с делением на ноль результат `null`, а не `NaN` или бесконечность;
- все агрегаты уважают один и тот же набор фильтров;
- ответ содержит `group_key`, `group_label` и запрошенные метрики;
- группировки по времени трактуют события в `Europe/Moscow`.

### 6.2. `GET /api/v1/analytics/reservations`

Параметры:

- фильтры даты бронирования `booked_from`, `booked_to`, а также даты мероприятия и предметных атрибутов события;
- `interval=day|week|month` для временного ряда (неделя начинается в понедельник);
- `group_by=none|genre|venue|artist|district|day|week|month`;
- `metrics=reservation_count,sold_tickets,revenue_rub,cancelled_count`.

Правила:

- `reservation_count`: количество подтверждённых бронирований;
- `sold_tickets`: сумма `quantity` подтверждённых бронирований;
- `revenue_rub`: сумма **зафиксированных** `total_price_rub` по подтверждённым бронированиям;
- `cancelled_count`: количество отменённых бронирований, независимо от текущих продаж;
- фильтр `booked_from`/`booked_to` относится к `booked_at`, **не** к `starts_at`;
- пустой результат обрабатывается корректно; отсутствие данных не подменяется фиктивным прогнозом.

**Важный учебный компромисс:** агрегаты позволяют не выгружать в браузер тысячи строк ради простых метрик. Однако индивидуальные рейтинги, правила отбора, поиск аномалий, объяснения, составление маршрута вечера и прогнозные критерии остаются логикой frontend. Преподаватель вправе отдельно потребовать от конкретных студентов самостоятельного расчёта выбранных метрик по исходным страницам API.

### 6.3. Сложные сценарии, доступные без специального endpoint

API обязан давать достаточно данных для следующих задач:

- интервалы `starts_at`/`ends_at` и координаты — проверка совместимости двух-трёх мероприятий;
- `price_rub`, `age_rating`, `available_tickets` — подбор для семьи/компании;
- артист/площадка и интервал — поиск пересечений расписаний;
- история `booked_at` + количество и остаток — простая оценка риска распродажи;
- цены по сравнимым группам — выявление статистических аномалий;
- статусы и необязательные поля — аудит качества данных;
- фильтры и bulk — массовая редактура и клиентский импорт.

## 7. Небольшой стартовый набор данных

### 7.1. Принцип

Стартовый набор **достаточен для знакомства с API и демонстрации интерфейса**, но намеренно **недостаточен для содержательной большой аналитики**. Объёмная работа с данными должна стимулировать ввод, импорт и обмен между студентами.

Рекомендуемый состав **одинакового базового seed**:

| Сущность | Количество | Требования |
|---|---:|---|
| Жанры | 8–10 | Концерт, театр, стендап, лекция, выставка, фестиваль и др. |
| Площадки | 10 | Несколько округов Москвы; минимум 9 с координатами |
| Артисты | 14 | Разные жанры, минимум два похожих имени |
| Серии | 3 | По 2–4 связанных события |
| Мероприятия | 36 | Около 12 прошедших и 24 предстоящих относительно `reference_time` |
| Бронирования | 60 | Разные даты, количества, цены, подтверждения и отмены |

Числа являются **критериями проектирования seed**, а не ограничениями БД.

### 7.2. Содержательные тестовые ситуации в seed

Обязательны примеры:

- бесплатное событие (`price_rub=0`) и дорогое событие;
- разные возрастные категории, в том числе `18+`;
- одно распроданное событие, одно почти распроданное и несколько без бронирований;
- прошедшее, предстоящее, отменённое и черновое события;
- несколько событий одного артиста и одной площадки;
- два события одной серии, некоторые с пересечением времени (для задач поиска конфликтов);
- площадка с корректными координатами и площадка без них;
- минимум два мероприятия в радиусе 3 км от **заранее задокументированной контрольной точки** Москвы и одно дальше радиуса;
- данные для вычисления среднего, медианы и группировок по жанрам;
- несколько бронирований разных дней для графика динамики;
- по крайней мере одна запись, требующая ручной проверки качества (например, необязательное описание отсутствует).

**Для адресов seed:** использовать реально существующие, вручную проверенные московские адреса и координаты. События, артисты и названия могут быть вымышленными. Нельзя подставлять произвольные координаты к настоящему адресу без проверки соответствия.

### 7.3. Инициализация

1. При первом запуске **пустой** БД применяются миграции и создаётся seed.
2. Генерация детерминирована: фиксированная версия seed и зафиксированное `reference_time`.
3. **Повторный запуск приложения не изменяет и не дополняет** существующую БД.
4. Если в БД уже есть пользовательские записи или импортированный дамп — сидирование запрещено.
5. Переменная `SEED_MODE=sample|empty` задаёт поведение **только на пустой базе**; по умолчанию `sample`.
6. Большого режима (`large`, `10000`, `stress`) в студенческой поставке **нет**.
7. Возможность заново получить seed предоставляется **явной командой очистки учебного volume**, с предупреждением о потере данных, а не простым рестартом.
8. `reference_time` хранится в БД и возвращается `/meta`; после импорта чужих данных используется время **импортированного набора**, а не значение из нового `.env`.

### 7.4. Как студенты наращивают данные

Backend предоставляет **инструменты**, но не готовый большой набор:

- создание и редактирование объектов через CRUD;
- массовое создание через `/events/bulk`;
- клиентский CSV-импорт (студент реализует UI и сопоставление полей);
- копирование/создание событий сериями;
- создание и отмену бронирований;
- операции массового изменения цен, статусов и расписания.

Никаких внешних «секретных» датасетов или автоматического добавления тысяч записей не требуется. Большой набор является **артефактом работы того, кто его подготовил**, и поступает другим только в процессе согласованного обмена.

## 8. Экспорт, импорт и совместимость студенческих баз

### 8.1. Основной способ переноса

Перенос — через **логический дамп PostgreSQL** (`pg_dump` в формате `custom`, затем `pg_restore`). Не пересылать физические файлы Docker volume как основной учебный формат.

Причины:

- физический volume зависит от версии PostgreSQL, структуры файлов и окружения;
- логический архив переносимее между машинами;
- преподавателю легче организовать воспроизводимую проверку;
- можно проверить состав и метаданные набора.

### 8.2. Обязательный комплект обмена

1. `dataset.dump` — архив PostgreSQL **со схемой и данными**, включая `DatasetMetadata`;
2. `dataset-manifest.json` — манифест:

```json
{
  "dataset_id": "<uuid>",
  "schema_version": "2026_01",
  "backend_version": "1.0.0",
  "postgres_major": 17,
  "postgis_major_minor": "3.6",
  "reference_time": "2027-03-01T00:00:00+03:00",
  "counts": {
    "venues": 40,
    "artists": 65,
    "events": 280,
    "reservations": 900
  },
  "sha256": "<SHA-256 dataset.dump>"
}
```

Значения — иллюстрация **чужой расширенной базы**, а не содержимого стартового seed.

### 8.3. Пример экспорта

При сервисе БД с именем `db`, БД `lab` и пользователе `lab`:

```bash
docker compose exec -T db \
  pg_dump -U lab -d lab -Fc --no-owner --no-acl > dataset.dump
```

Создание JSON-манифеста можно автоматизировать отдельным преподавательским скриптом. Дамп сам по себе не следует добавлять в обычную историю Git, если он велик: передавайте его отдельно или по согласованному каналу.

### 8.4. Пример импорта

Импорт **только в отдельную пустую учебную БД** с совместимой версией PostGIS. После запуска одного сервиса БД (без backend, чтобы он не успел создать seed):

```bash
docker compose up -d db

docker compose exec -T db \
  pg_restore -U lab -d lab \
  --no-owner --no-acl --single-transaction \
  < dataset.dump
```

Далее запускается backend/frontend. Команды — пример для новой базы без предметных таблиц; если созданную PostgreSQL БД уже заполнил seed, её сначала пересоздают **как пустую** по отдельно документированной процедуре. Перед импортом следует проверить SHA-256 архива и совместимость манифеста.

**Нюанс PostGIS:** чистая БД контейнера может уже содержать расширение `postgis`; импорт логического дампа и миграции должны быть протестированы с таким состоянием. Скрипт восстановления обязан учитывать системные объекты расширения и не требовать их повторного создания владельцем без прав.

### 8.5. Проверки после импорта

- `/health/ready` возвращает успех.
- `/api/v1/meta` показывает импортированные `dataset_id`, `schema_version` и `reference_time`.
- Количества записей совпадают с манифестом.
- Геопоиск работает, GiST-индекс создан.
- Запуск backend **не возвращает исходные 36 мероприятий** поверх импортированных данных.
- Новый фронтенд не зависит от UUID и конкретных названий из своей исходной БД.
- При последующих перезапусках данные сохраняются.

## 9. Валидация, ошибки и консистентность

### 9.1. Коды ответа

| Код | Ситуация |
|---|---|
| `200` | Успешное чтение/обновление |
| `201` | Создан ресурс |
| `204` | Удалён ресурс без тела |
| `400` | Неверный формат запроса или параметров |
| `404` | Ресурс не найден |
| `409` | Конфликт состояния (недостаток билетов, ссылки на удаляемую запись, повтор ключа с иным содержимым) |
| `422` | Значение не прошло предметную валидацию |
| `503` | Backend не готов / БД недоступна |

Единый формат ошибки:

```json
{
  "error": {
    "code": "INSUFFICIENT_TICKETS",
    "message": "Недостаточно доступных билетов",
    "details": {
      "event_id": "87cc5a69-a922-4b97-8999-bebc253bd3cd",
      "requested": 3,
      "available": 2
    }
  }
}
```

Машинные коды ошибок документируются и не меняются произвольно. Не выводить SQL, секреты, stack traces и строки подключения в HTTP-ответах.

### 9.2. Обязательные проверки

- Положительная вместимость и квота; квота не превышает вместимость площадки.
- Квота не может стать меньше числа подтверждённых забронированных билетов.
- Цена неотрицательна, а количество бронируемых билетов положительно.
- Начало мероприятия раньше окончания.
- Координаты либо обе отсутствуют, либо обе валидны.
- Невозможно сослаться на несуществующих артиста, площадку, событие или серию.
- Невозможно создать бронирование для неопубликованного/отменённого/архивного мероприятия.
- При отмене мероприятия его подтверждённые бронирования отменяются атомарно.
- Запрещены некорректные значения перечислений, неизвестные поля массовых операций, невалидные параметры сортировки.
- В производной статистике нельзя получить отрицательный остаток мест или бесконечный процент.

**Важно:** предупредительные проблемы (возможные дубликаты, пустое описание, пересечения расписаний) **не всегда блокируют сохранение** — они нужны для учебных заданий на поиск и исправление дефектов данных.

### 9.3. Работа с браузером

- Фронтенд обращается к API относительными URL `/api/v1/...` через NGINX, раздающий фронтенд.
- NGINX и backend находятся в общей Docker-сети; прокси сохраняет путь запроса и передаёт заголовки `Content-Type` и `Idempotency-Key`.
- Все JSON-ответы имеют корректный `Content-Type` и UTF-8; русский текст поддерживается.
- Предусмотреть понятные ответы для пустого списка, несуществующего ID и временной недоступности БД.

## 10. Нефункциональные требования

### 10.1. Надёжность

- `docker compose up -d` + запуск backend должен быть достаточен для развёртывания пустого учебного окружения.
- У БД есть `healthcheck`; backend ждёт готовности БД и применяет миграции до ответа `/health/ready`.
- Повторный запуск сервиса не приводит к дублированию seed, потере данных или повторным продажам.
- Все изменения бронирований и массовые изменения транзакционны.
- Данные хранятся в именованном Docker volume.

### 10.2. Производительность

Целевой класс данных — **до 10 000 мероприятий**, **до 2 000 площадок**, **до 100 000 синтетических бронирований** после обмена между студентами. Это **не объём seed**.

При разработке преподавательского backend желательно проверить на специально созданной во время тестирования базе:

- фильтры/пагинация/справочники;
- пространственный поиск с GiST;
- групповые агрегации;
- конкурентное бронирование;
- импорт/восстановление дампа.

Рекомендуемые цели на обычном учебном ноутбуке после прогрева: типовой список до 500 мс, геопоиск до 1 с, агрегированный запрос до 2 с. Это **ориентиры для испытаний**, а не гарантированные универсальные SLA. Большая нагрузочная тестовая база используется преподавателем при разработке и не включается в студенческую поставку.

### 10.3. Безопасность и приватность

- Предназначение — **локальная учебная среда**, не публичный production-сервис.
- Не хранить реальные персональные данные и платёжные сведения.
- БД по умолчанию не публикует порт на хост; работает во внутренней Compose-сети.
- Пароли задаются через `.env`, не фиксируются в репозитории.
- Логи не содержат секретов.
- Дампы от других студентов считаются недоверенными: проверяется источник, контрольная сумма, формат и версия, восстановление — **только в изолированную тестовую БД**.
- Запуск SQL-скриптов из непроверенного архива на машине преподавателя/других студентов не допускается без отдельной проверки.

## 11. Пример базового Compose-контракта

> Это образец **преподавательской проверки** DB+backend, а не готовый студенческий `compose.yml`; имя и тег образа backend в примере условны.

```yaml
services:
  db:
    image: postgis/postgis:17-3.6
    environment:
      POSTGRES_DB: ${PG_DB_NAME}
      POSTGRES_USER: ${PG_USER_NAME}
      POSTGRES_PASSWORD: ${PG_USER_PASSWORD}
    volumes:
      - pgdata:/var/lib/postgresql/data
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U \"$$POSTGRES_USER\" -d \"$$POSTGRES_DB\""]
      interval: 5s
      timeout: 3s
      retries: 20

  backend:
    image: ghcr.io/example-org/moscow-events-api:1.0.0
    environment:
      PG_HOST: ${PG_HOST:-db}
      PG_PORT: ${PG_PORT:-5432}
      PG_DB_NAME: ${PG_DB_NAME}
      PG_USER_NAME: ${PG_USER_NAME}
      PG_USER_PASSWORD: ${PG_USER_PASSWORD}
    depends_on:
      db:
        condition: service_healthy
    ports:
      - "8000:8000"

volumes:
  pgdata:
```

Подготовить `.env.example` с пятью переменными `PG_HOST`, `PG_PORT`, `PG_DB_NAME`, `PG_USER_NAME`, `PG_USER_PASSWORD` (без действительных секретов) и инструкцию копирования в `.env`; проверить, что пароль не коммитится. Образ backend может поддерживать переменную учебного времени/версии seed, но **не должен пересоздавать существующую БД**.

**Примечание по версиям:** PostgreSQL 17 использует стандартный путь `/var/lib/postgresql/data` для volume. В PostgreSQL 18 путь монтирования изменился; поэтому в потоке необходимо закрепить и образ, и путь, а не смешивать примеры от разных major-версий.

## 13. Критерии приёмки преподавательского backend

### 13.1. Инфраструктурные

- [ ] Чистый запуск PostgreSQL+PostGIS+backend проходит по README.
- [ ] Расширение `postgis` активировано; пространственный GiST-индекс существует.
- [ ] Миграции не требуют ручного подключения к БД.
- [ ] `/health/ready` корректно отражает готовность.
- [ ] `/openapi.json` содержит все методы, модели, query-параметры, ответы и ошибки.
- [ ] `docker compose down` / повторный `up` сохраняет изменения.
- [ ] Тест на поддерживаемых архитектурах ноутбуков студентов пройден.

### 13.2. Данные

- [ ] Seed содержит только **малый набор** с заданными разнообразными случаями.
- [ ] Второй запуск не добавляет записи и не меняет `dataset_id`.
- [ ] Есть возможность создать существенно больше записей только пользовательскими операциями/API.
- [ ] Взаимосвязи артисты—мероприятия—площадки—бронирования непротиворечивы.
- [ ] Выручка считается по снимкам цен, занятость — по подтверждённым броням.
- [ ] Отмена мероприятия корректно отменяет связанные бронирования.

### 13.3. Функциональные

- [ ] Полный CRUD предусмотренных сущностей работает с документированной валидацией.
- [ ] Все списки поддерживают пагинацию, фильтрацию и детерминированную сортировку.
- [ ] `POST /events/bulk` делает настоящий preview и атомарное применение.
- [ ] Одновременные запросы бронирования не приводят к overselling.
- [ ] `GET /events/nearby` включает точки внутри радиуса, исключает точки вне него и возвращает метры.
- [ ] Координаты не перепутаны: HTTP `latitude, longitude`; PostGIS/GeoJSON — `longitude, latitude`.
- [ ] GeoJSON корректно открывается в типичном веб-картографическом клиенте.
- [ ] Универсальные агрегаты дают корректные значения на контрольной базе, включая пустые группы.

### 13.4. Межстуденческий обмен

- [ ] Созданный студентом дамп может восстановить другой студент в чистую базу.
- [ ] После восстановления **не срабатывает повторный seed**.
- [ ] Манифест и `/dataset/summary` согласованы с количеством записей.
- [ ] Восстановленный набор виден через тот же API без изменений frontend.
- [ ] Составлен краткий регламент обмена и проверки ошибок восстановления.

### 13.5. Минимальные автоматизированные тесты

1. **Пустая БД → seed:** проверка количеств, версий и тестовых случаев.
2. **Рестарт → нет повторного seed.**
3. **CRUD → чтение → обновление → допустимое удаление.**
4. **Параметры фильтра:** стоимость, жанр, возраст, интервал, остаток мест.
5. **ГИС:** точка на расстоянии 0 м, внутри радиуса, вне радиуса, без координат, перепутанные широта/долгота.
6. **Бронирование:** последняя доступная квота, попытка перепродажи, повтор с `Idempotency-Key`, отмена, цена-снимок.
7. **Bulk:** предпросмотр без записи, корректный пакет, пакет с ошибкой и полный rollback.
8. **Агрегаты:** среднее и медиана, процент заполняемости, выручка, нулевой знаменатель, отменённые брони.
9. **Обмен:** экспорт, восстановление в чистую БД, отсутствие seed, функциональная проверка чужого набора.
10. **Независимость frontend:** отсутствующие необязательные поля, пустые списки, изменённые имена и UUID, увеличенный объём данных.

## 15. Принятые решения и вопросы перед реализацией

**Зафиксировать заранее:**

1. Список жанров и правила его изменения (рекомендуется фиксированный справочник в версии `v1`).
2. Уровень района: административные округа Москвы или более мелкие районы; смешение уровней нежелательно.
3. Дату `reference_time` и состав контрольного seed на семестр.
4. Политику статусов событий, особенно отмены с бронированиями.
5. Максимальный размер одного bulk-пакета (предложено 200).
6. Поддерживаемые CPU-архитектуры студентов и образ PostGIS для каждой.
7. Единая точка входа для браузера — NGINX фронтенда; запросы `/api/v1` передаются backend через общую Docker-сеть.

**Рекомендуемое решение для первого потока:** использовать PostGIS, фиксировать PostgreSQL 17/PostGIS 3.6, поддерживать один обязательный общий API, создавать небольшой одинаковый seed и передавать большие пользовательские базы исключительно логическими дампами. Это даёт содержательный геопоиск без необходимости разворачивать геокодер, сервис маршрутизации или отдельную ГИС-инфраструктуру.
